  <name>Task 2: Create download-helper utility with ApexLog query and streaming support</name>
  <files>src/utils/download-helper.ts</files>
  <action>
Create new file `src/utils/download-helper.ts` with functions for querying and downloading ApexLog records.

Export the following functions:

1. `queryApexLogsForUser(connection: Connection, userId: string, startTime: Date, endTime: Date): Promise<ApexLogRecord[]>`
   - Build SOQL query matching RESEARCH.md Pattern 1: SELECT Id, LogUserId, LogUser.Name, StartTime, LogLength, DurationMilliseconds, Status FROM ApexLog WHERE LogUserId = ? AND StartTime >= ? AND StartTime <= ? ORDER BY StartTime DESC
   - Use connection.tooling.query() to execute
   - Handle pagination: if result.totalSize > 2000, loop with OFFSET to fetch all records (see RESEARCH.md Common Pitfalls § Pagination Loss)
   - Return array of ApexLogRecord
   - Per UX-03 requirement, wrap query call with executeWithRetry() to handle HTTP 429 rate limiting

2. `executeWithRetry<T>(operation: () => Promise<T>, maxAttempts: number = 3): Promise<T>`
   - Exponential backoff retry helper per RESEARCH.md Pattern 6
   - Catch error.status === 429 (HTTP Too Many Requests)
   - On 429: calculate delay = 2^(attempt-1) * 1000ms, await, retry
   - On other errors or maxAttempts exceeded: throw error
   - Use for queryApexLogsForUser, tooling API queries, and bulk delete operations in purge command

3. `calculateETA(bytesDownloaded: number, totalBytes: number, elapsedSeconds: number): number`
   - Return estimated time remaining in seconds
   - Formula: (totalBytes - bytesDownloaded) / (bytesDownloaded / elapsedSeconds)
   - Handle division by zero: return 0 if elapsedSeconds < 1 or currentRate is 0
   - Per DOWNLOAD-02 requirement (progress tracking with ETA)

4. `streamDownloadToFile(readableStream: NodeJS.ReadableStream, filePath: string): Promise<void>`
   - Use fs.pipeline() from stream/promises module per RESEARCH.md Pattern 2
   - Creates writable stream to filePath
   - Calls fs.pipeline(readable, writable) and awaits completion
   - On error, pipeline automatically cleans up both streams
   - Handles large files (10-100MB) without buffering in memory per DOWNLOAD-05

Imports:
- `{ Connection } from @salesforce/core`
- `{ pipeline } from 'stream/promises'`
- `{ createWriteStream } from 'fs'`
- `ApexLogRecord, DownloadProgress` from `../types/download`

Per RESEARCH.md, do NOT use hand-rolled streaming or manual chunk buffering. Use fs.pipeline() which handles backpressure automatically.

Do NOT buffer entire files in memory (anti-pattern per RESEARCH.md Pitfall 1).

Error handling: catch errors from pipeline(), tooling API queries, and rate limiting. Propagate to caller for context-specific handling.

  <name>Task 4: Create quota-calculator utility for storage limit enforcement</name>
  <files>src/utils/quota-calculator.ts</files>
  <action>
Create new file `src/utils/quota-calculator.ts` with functions for checking org storage quota.

Export the following functions:

1. `async getRemainingQuota(connection: Connection): Promise<{ usedMB: number; remainingMB: number; totalMB: number }>`
   - Query org's remaining debug log storage quota
   - Primary approach (preferred): Use REST Limits API per RESEARCH.md Pattern 3, Option A
   - Make request to `/services/data/v67.0/limits` endpoint using connection.request()
   - Parse response.DebugLogs.Max (total bytes) and response.DebugLogs.Remaining (remaining bytes)
   - Convert to MB: divide by 1e6
   - Return object: { usedMB: (Max - Remaining) / 1e6, remainingMB: Remaining / 1e6, totalMB: Max / 1e6 }
   - If REST Limits API fails or field unavailable, fallback to aggregation (see below)
   - Per UX-03 requirement, wrap call in executeWithRetry() to handle HTTP 429

2. `async getRemainingQuotaFallback(connection: Connection): Promise<{ usedMB: number; remainingMB: number; totalMB: number }>`
   - Fallback if REST Limits API unavailable: aggregate ApexLog.LogLength from all records
   - Query: SELECT SUM(LogLength) totalSize FROM ApexLog
   - Calculate: usedBytes = totalSize || 0, remainingBytes = 1e9 - usedBytes
   - Return in MB format same as primary approach
   - Per RESEARCH.md Pattern 3, Option B

3. `async validateQuotaAvailable(connection: Connection, requiredBytes: number): Promise<boolean>`
   - Check if org has sufficient quota to download requiredBytes
   - Call getRemainingQuota() to get current remaining
   - Return remainingMB * 1e6 >= requiredBytes
   - If quota exceeded, throw error with formatted message per D-05: "Storage quota exceeded. Current: {usedMB}MB/{totalMB}MB. Run: sf log purge to delete old logs."
   - Per DOWNLOAD-03 and DOWNLOAD-04 requirements, validate quota enforcement

4. `formatQuotaMessage(usedMB: number, remainingMB: number, totalMB: number): string`
   - Return human-readable quota status: "Used: {usedMB}MB / {totalMB}MB (Remaining: {remainingMB}MB)"
   - Round to 1 decimal place for readability

Imports:
- `{ Connection } from @salesforce/core`
- `{ executeWithRetry }` from `./download-helper`

Per RESEARCH.md Common Pitfalls § Pitfall 2, check quota **during** download progress, not upfront. This quota-calculator validates at multiple checkpoints as download proceeds.

Per RESEARCH.md, REST Limits API is more accurate than aggregation (org-wide view vs. expensive query); use as primary, fallback to aggregation if API unavailable.

Error handling: Catch HTTP 429 and retry via executeWithRetry(). Catch other API errors and provide actionable message. Do NOT fail silently; propagate error to caller with context.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Salesforce API → Plugin | Tooling API ApexLog records contain user-generated log data; quota values returned via REST Limits API |
| Local filesystem | Plugin writes log files to user's home directory; must sanitize paths to prevent traversal attacks |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-01 | Tampering | ApexLog.LogLength from query result | mitigate | Validate LogLength is positive integer; reject if > 1e9; use parsed JSON from tooling.query(), not string concatenation |
| T-03-02 | Tampering | Local file path construction (userId in path) | mitigate | Use path.join() only; never concatenate strings; path.join() blocks `../` escapes; validate userId is alphanumeric before use |
| T-03-03 | Denial | Memory exhaustion via large ApexLog body download | mitigate | Use fs.pipeline() streaming; never buffer entire file in memory; enforce max timeout on connection.request() calls |
| T-03-04 | Tampering | REST Limits API response (quota values) | mitigate | Validate Max > Remaining; both are positive integers; reject if response format unexpected (fallback to aggregation) |
| T-03-05 | Denial | Rate limiting DoS via unlimited retries | mitigate | Cap retries at 3 attempts; use exponential backoff (2^n delays); fail fast after max attempts exceeded (UX-03 requirement) |
| T-03-06 | Tampering | SIGINT during download leaves partial files | mitigate | Catch SIGINT signal in download handler; clean up partial files before exit; track completion state in metadata |
| T-03-SC | Tampering | No new packages installed Phase 3 | accept | All dependencies already validated in Phase 0 research; no new npm packages introduced |

</threat_model>
