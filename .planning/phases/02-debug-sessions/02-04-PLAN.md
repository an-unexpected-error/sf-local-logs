Update `src/commands/log/trace.ts` run() method to add interactive search when --user-id not provided. Implementation:

   - Check if --user-id flag is provided
   - If provided: skip to existing logic (explicit bypass for scripting, per D-16)
   - If NOT provided: enter interactive search flow (per D-13)

2. **Interactive search flow (add method selectUserInteractively):**
   - Display prompt: messages.getMessage('promptSearchTerm') with example "(e.g., 'john' or 'smith')"
   - Get search term from user via `input({ message, validate })` from @inquirer/prompts
   - Validate: search term >= 2 characters, provide error message if too short
   - Catch Ctrl+C (user cancels): display message "Search cancelled. No trace flag created." and exit with code 0

3. **Execute search (reuse Phase 1 logic):**
   - Call `buildSearchQuery(searchTerm)` from src/utils/soql-builder.ts
   - Execute via `org.getConnection().query(buildSearchQuery(searchTerm))`
   - Get results array of User objects

4. **Handle empty results (per D-17):**
   - If results.length === 0:
     - Display message: messages.getMessage('messageNoUsersFound', [searchTerm])
     - Prompt user: "Try searching again? (y/n)" or automatically retry the search flow
     - Loop back to search term prompt (allow multiple attempts)

5. **Display results and select user (per D-14, D-15):**
   - Format results into table format: ID | Name | Email | Last Login (using Phase 1's date-formatter.ts)
   - Use cli-ux.table() to display results (same as Phase 1)
   - If multiple results: show all results and indicate pagination
   - If results == 20 (hit limit): display message indicating "20 of N users shown; refine search to narrow results"
   - Selection strategy (per D-15, immediate trace creation):
     - If only 1 result: automatically select it (no prompt needed)
     - If multiple results: prompt user "Select a user (enter ID or index)" or use keyboard selection via @inquirer/prompts select() with user names/IDs
     - Simplified for v1: use first result if auto-selection enabled, or prompt to confirm first result
   - Extract selected user's ID and proceed to trace creation

6. **Continue with trace creation:**
   - After userId selected, continue with existing Wave 2/3 logic (DebugLevel query, trace creation, watch mode)

**Error handling:**
- SOQL execution error: display "Search query failed. Try again." and offer retry
- User not found post-search: should not happen (we got results), but if profile/permission changes, handle gracefully
- Catch all errors and offer retry or exit

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| User input (search term) → SOQL query | Search term enters SOQL construction via buildSearchQuery |
| User selection (keyboard) → trace creation | Selected user ID flows into TraceFlag creation |
| Salesforce API response → display | User details returned from search query; sensitive data filtered |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-16 | Tampering | SOQL injection via search term | mitigate | Use escapeSoql() from Phase 1 before building query; prevents single quote injection |
| T-02-17 | Information Disclosure | User cancels search, partial results leaked | accept | Results only displayed to authenticated user in their own org; cancellation clears display |
| T-02-18 | Denial | User enters very long search term, causing DoS | mitigate | Validate search term length (2-100 chars); LIMIT 20 on query results |
| T-02-19 | Spoofing | Selected user ID is forged/invalid | accept | Salesforce API validates user ID at trace creation time; invalid ID shows error |
| T-02-20 | Information Disclosure | Search results displayed with email addresses | accept | Email is in User query results (legitimate admin need); only visible to authenticated admin |
</threat_model>
