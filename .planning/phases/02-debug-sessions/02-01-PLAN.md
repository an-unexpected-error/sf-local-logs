  <action>
Create new file `src/utils/trace-helper.ts` with four helper functions (per RESEARCH.md Code Examples and Patterns 1-4):

1. **getDefaultDebugLevel(org: Org): Promise<string>**
   - Query org's default DebugLevel using jsforce.tooling.query()
   - First attempt: query by DeveloperName = 'Debug'
   - Fallback: query most recently created DebugLevel (ORDER BY CreatedDate DESC)
   - Return the ID field
   - Throw descriptive error if no DebugLevel found (include error message for user)
   - Per RESEARCH.md Pitfall 1, must handle edge case where org has no default

2. **createTraceFlag(org: Org, userId: string, debugLevelId: string): Promise<{ id: string; expirationDate: string; debugLevel: string }>**
   - Create TraceFlag via jsforce.tooling.create('TraceFlag', {...})
   - Set StartTime = now, ExpirationDate = now + 24 hours (24*3600*1000 milliseconds)
   - Convert both to ISO 8601 format via toISOString()
   - Check result.success; if false, throw error with result.errors[0].message
   - Catch INVALID_FIELD, NOT_AUTHORIZED, DUPLICATE_VALUE and throw meaningful errors
   - Return { id, expirationDate, debugLevel } for display
   - Per RESEARCH.md Pitfall 4, validate date calculations

3. **checkExistingTraceFlag(org: Org, userId: string, overwrite: boolean): Promise<{ exists: boolean; id?: string }>**
   - Query Tooling API for active TraceFlag (ExpirationDate > now)
   - If found and overwrite=false, throw error message: "User already has an active trace flag. Use --overwrite to stop existing trace and create a new one."
   - If found and overwrite=true, update the existing TraceFlag's ExpirationDate to NOW (stopping it), then return { exists: true, id: existingId }
   - If not found, return { exists: false }
   - Per RESEARCH.md Pitfall 6, use exact field names (TracedEntityId, ExpirationDate)

4. **getDebugLevelName(org: Org, debugLevelId: string): Promise<string>**
   - Query DebugLevel by ID to get DeveloperName field for display
   - Return DeveloperName (e.g., "Debug", "Info") for human-readable output in trace confirmation
   - Fallback to returning the ID if query fails (don't break trace creation)

Import Org from @salesforce/core; use org.getConnection() to get authenticated jsforce Connection. All functions are async. Include try/catch blocks with proper error message translation (not raw Salesforce API errors).

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| CLI input → Salesforce API | User-provided user ID or search term crosses into Salesforce API |
| Salesforce API response → display | Trace flag details returned from API may contain sensitive info (should be filtered) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-01 | Tampering | TraceFlag creation with forged user ID | mitigate | Do not pre-validate user ID (per D-19); let Salesforce API enforce permission boundary; catch and display permission errors |
| T-02-02 | Information Disclosure | DebugLevel query failure exposes API details | mitigate | Catch query errors and return generic "Unable to determine debug level" message to user; log raw error only in --debug mode |
| T-02-03 | Denial | Unbounded polling in watch mode | mitigate | Fixed 1-second polling interval; LIMIT 1 on all Tooling queries; 24-hour max enforced by Salesforce |
| T-02-04 | Information Disclosure | Credentials exposed in error logs | mitigate | Never log org credentials, access tokens, or connection details; @salesforce/core handles credential storage securely |
| T-02-05 | Spoofing | User ID validation bypassed | accept | Per D-19, Salesforce API validates; no pre-flight validation in Phase 2; remediation message guides users to provide valid ID |
| T-02-SC | Tampering | cli-progress installation from npm registry | mitigate | Confirmed [ASSUMED] legitimacy via RESEARCH.md Package Legitimacy Audit (6+ years, 800k/week, active repo); slopcheck will verify on install |
</threat_model>
