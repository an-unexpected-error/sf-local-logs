## Summary

Phase 0 establishes the Salesforce CLI plugin framework by scaffolding a TypeScript project, configuring build infrastructure, linting, testing, and local development tools. The foundation is built on `plugin-template-sf`, an official Salesforce-provided scaffold that includes oclif v4 command framework, @salesforce/sf-plugins-core for plugin utilities, and @salesforce/dev-scripts for development standards enforcement.

The phase addresses three locked requirements: plugin installation via `sf plugin install` (INSTALL-01), Salesforce CLI v2.x+ compatibility (INSTALL-02), and Node.js 18.0.0+ enforcement (INSTALL-03). Local development setup includes scratch org tooling and `sf plugin link` for testing before publication. GitHub Actions workflows automate linting, building, and testing to catch issues early.

**Primary recommendation:** Use `sf dev generate plugin` (provided by plugin-template-sf) to scaffold the complete project structure. This gives official, maintained defaults for all configuration. Verify Node.js version via `engines: { "node": ">=18.0.0" }` in package.json (enforced automatically by npm at install time). Configure three GitHub Actions workflows: lint (eslint), build (typescript compilation), and test (mocha unit + integration tests).

## Architecture Patterns

### System Architecture Diagram

```
User Input (CLI)
      ↓
    oclif v4
      ↓
Command Class (SfCommand)
  ├─ Parse Flags (--target-org, --help, custom flags)
  ├─ Initialize Org (@salesforce/core)
  └─ Run business logic
      ↓
Salesforce Org
(via authenticated jsforce Connection)
      ↓
Org Responses
      ↓
Format Output (--json or human-readable)
      ↓
CLI Output
```

**Entry Points:**
- User runs `sf log <subcommand> [flags]`
- oclif dispatcher routes to `src/commands/log/<subcommand>.ts`

**Processing Stages:**
1. **Flag parsing** — oclif parses flags, validates org flag (requiredOrg/optionalOrg)
2. **Org initialization** — @salesforce/core authenticates to selected org
3. **Business logic execution** — Command runs async, calls jsforce APIs
4. **Result formatting** — Converts result to --json or human-readable output

**Decision Points:**
- Does command require an org? Use `Flags.requiredOrgFlag()` or `Flags.optionalOrgFlag()`
- Is result JSON-serializable? Use structured types with `Promise<T>` return type
- Need to prompt user? Use `this.confirm()` from SfCommand

**External Dependencies:**
- Salesforce org (authenticated via DevHub or saved org credentials)
- GitHub (for plugin distribution)
- npm registry (for `sf plugin install`)

**Key elements:**

### Anti-Patterns to Avoid

- **Don't use SfdxCommand** — Outdated (sfdx CLI). Use SfCommand from @salesforce/sf-plugins-core.
- **Don't hardcode org usernames** — Use Flags.requiredOrgFlag() to accept --target-org. Admins may have multiple orgs.
- **Don't write custom OAuth logic** — @salesforce/core handles auth. Use saved org credentials or DevHub.
- **Don't mix axios/fetch with jsforce** — jsforce Connection is already authenticated. Don't add another HTTP client.
- **Don't use Commander.js or yargs** — oclif is the standard. Mixing frameworks breaks plugin composition.
- **Don't forget --json output** — All commands must support --json flag for programmatic use. Return structured types from run().
- **Don't hardcode error messages in code** — Load from messages Markdown files via Messages.loadMessages(). This enables i18n and consistency.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Plugin scaffolding | Custom project structure | `sf dev generate plugin` (plugin-template-sf) | Template provides official structure, tests, CI/CD, linting defaults. Copying/inventing structure leads to compatibility issues. |
| Command registration & routing | Manual require() of commands | oclif (automatic directory discovery) | oclif discovers commands from src/commands/ structure automatically. Manual routing breaks plugin composition. |
| Org authentication | Custom OAuth token management | @salesforce/core Org class | Core handles DevHub login, credential storage, token refresh, multi-org contexts. Custom auth is a security/maintenance nightmare. |
| HTTP requests to Salesforce APIs | Custom fetch + manual auth | jsforce Connection (via org.getConnection()) | jsforce is already authenticated via org connection. Custom HTTP adds complexity without benefit. |
| Help text generation | Hardcoded strings in code | Messages Markdown files (oclif pattern) | Messages pattern enables i18n, separates help from code, integrates with --help. Hardcoding breaks consistency. |
| Error handling | Throw generic Error objects | SfError + Messages pattern | SfError integrates with CLI exit codes, --json output, and message templating. Custom errors lose CLI context. |
| Code quality enforcement | Manual eslint invocations | @salesforce/dev-scripts + eslint-plugin-sf-plugin | dev-scripts auto-enforces linting in package.json. Plugin rules catch Salesforce-specific anti-patterns. Manual setup drifts. |
| Test framework setup | Manual Mocha/Jest configuration | @salesforce/cli-plugins-testkit | Testkit provides scratch org fixtures, command execution helpers, and coverage config. Manual setup has gaps. |

**Key insight:** Salesforce provides plugin-template-sf and these libraries specifically because plugin development has many integration points with the CLI framework. Hand-rolling any of these invites compatibility issues, security problems, or maintenance burdens when the ecosystem evolves.

## Common Pitfalls

### Pitfall 1: Ignoring Node.js Version at Install Time

**What goes wrong:** Plugin is developed on Node.js 18, published to npm, but user tries to install with Node.js 16. Installation fails with cryptic "engine not compatible" error, leaving user confused.

**Why it happens:** Plugin author forgets to set `engines: { "node": ">=18.0.0" }` in package.json, or doesn't test installation on older Node versions. npm checks the engines field at install time, but only if set.

**How to avoid:** 
1. Always include `engines` field in package.json. Plugin template includes this by default.
2. Test installation locally: `npm install --save-optional <package>` should fail on Node <18.
3. Document minimum Node version in README.md.

**Warning signs:** User reports installation failure; error message mentions "The engine 'node' is incompatible with this module."

### Pitfall 2: Using SfdxCommand Instead of SfCommand

**What goes wrong:** Command won't register in sf CLI (expects SfCommand). Plugin appears broken after install; `sf log search` returns "command not found."

**Why it happens:** Copying code from older sfdx-based plugins or confusion between old/new Salesforce CLI versions. SfdxCommand is from sfdx (old), SfCommand is from sf (new, v2.x+).

**How to avoid:**
1. Always extend `SfCommand` from `@salesforce/sf-plugins-core` (not SfdxCommand).
2. Check TypeScript imports match: `import { SfCommand } from '@salesforce/sf-plugins-core'`.
3. eslint-plugin-sf-plugin linting rules should catch this.

**Warning signs:** TypeScript compilation succeeds, but command doesn't appear in `sf log --help`. Check command class parent.

### Pitfall 3: Hardcoded Org Username Instead of Flags.requiredOrgFlag()

**What goes wrong:** Command works in one user's environment (where org is aliased "dev-org"), but fails for others. Users can't use --target-org flag to override.

**Why it happens:** Tempting to hardcode testing org or forget that admins manage multiple orgs. Leads to inflexible commands.

**How to avoid:**
1. Always accept org via `Flags.requiredOrgFlag()` or `Flags.optionalOrgFlag()`.
2. Never hardcode org usernames in code.
3. Tests should mock org via TestSession, not assume a named org exists.

**Warning signs:** Command works for you, fails for others. Users ask "how do I specify a different org?"

### Pitfall 4: Not Exporting Messages to messages/ Directory

**What goes wrong:** `sf log search --help` shows no summary or examples. Command appears undocumented.

**Why it happens:** Forgetting to create messages/log.search.md file. oclif looks for help text in messages/, not in code.

**How to avoid:**
1. Create `messages/log.<commandname>.md` for each command.
2. Use H1 headers for keys: `# summary`, `# description`, `# examples.0.description`
3. Load in command via `Messages.loadMessages('plugin-name', 'log.<commandname>')`

**Warning signs:** `--help` output is sparse or missing command description.

### Pitfall 5: Skipping .nut.ts Tests (Integration Tests)

**What goes wrong:** Plugin compiles, unit tests pass, but fails when users install and run `sf plugin link . && sf log search`. Command registration or org interaction issues surface post-install.

**Why it happens:** Unit tests are fast and run locally. NUT (integration) tests require scratch org setup, so developers skip them. But unit tests don't catch plugin registration or real Salesforce API issues.

**How to avoid:**
1. Write .nut.ts tests for any command that touches org or plugin framework.
2. Run both `yarn test` (units) and `yarn test:nut` (integration) before push.
3. CI/CD should run both suites.

**Warning signs:** All unit tests green, but `sf plugin link . && sf log search` fails or returns unexpected output.

### Pitfall 6: Forgetting --json Support

**What goes wrong:** Command works for CLI output, but fails when user runs with --json flag. Output isn't valid JSON, causing parsing errors in scripts.

**Why it happens:** Return type isn't serializable, or command logs extra text alongside JSON output. oclif passes --json flag automatically, but command must honor it.

**How to avoid:**
1. Always return a typed result from `run(): Promise<T>`. Example: `return { id: '...', name: '...' }`.
2. Don't use `this.log()` when result will be JSON. Instead, return data in result object.
3. Test with `--json` flag: `sf log search --json | jq .`

**Warning signs:** `sf log search --json` returns mixed text and JSON, or throws parse error.

### Known Threat Patterns for Salesforce CLI Plugins

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Hardcoded credentials in plugin code | Information Disclosure | Never hardcode org usernames/passwords. Always use @salesforce/core Org auth and saved credentials. |
| Unauthenticated API calls | Authentication | All plugin calls go through org.getConnection(), which is pre-authenticated by @salesforce/core. |
| Command injection via unvalidated flags | Tampering | Use oclif flag types (string, url, directory) for validation. Don't construct SOQL or shell commands from user input. |
| Privilege escalation (admin override) | Elevation | Commands inherit org's permission context. Respect requiredOrgFlag; don't bypass user's org choice. |
| Data exfiltration (large log downloads) | Information Disclosure | Phase 3 will implement 1GB storage quota checks and streaming I/O. Phase 0 is scaffolding only. |
| Malformed error messages leaking secrets | Information Disclosure | Load error messages from messages Markdown files. Don't include org names, tokens, or sensitive data in error output. |

**No critical security issues identified for Phase 0** (scaffolding phase). Security validation begins in Phase 1 when commands interact with org data.
